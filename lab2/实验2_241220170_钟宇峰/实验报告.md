# 校园二手交易平台 软件设计报告（实验二）

学号：241220170　姓名：钟宇峰

本系统面向单个校区的学生二手物品交易，覆盖商品发布、审核、检索、预约与线下交易闭环；交易在线下当面完成，不涉及在线支付、物流与担保交易。

---

## 一、软件的主要功能

| 模块 | 主要功能 | 对应需求 |
|---|---|---|
| 账号与权限 | 手机号/学号注册（昵称、联系方式必填）、登录、修改资料、卖家身份申请与审核、账号封禁与解封、封禁登录提示 | REQ-001~004、REQ-016、REQ-017 |
| 商品与审核 | 商品信息维护、保存草稿、提交审核、管理员审核通过/驳回、卖家下架 | REQ-005~008、REQ-014 |
| 预约与交易 | 发起预约、取消预约、卖家确认预约、交易完成 | REQ-010~013、REQ-019 |
| 违规处置 | 违规下架商品、封禁账号，并级联删除相关预约记录 | REQ-015、REQ-016 |
| 查询与统计 | 关键词/分类/价格区间/状态组合查询、卖家与平台统计报表 | REQ-009、REQ-022 |
| 操作日志 | 关键操作留痕、按时间/操作人/对象查询、不可篡改 | REQ-021 |

### 1.1 状态定义

- **商品（8 种）**：草稿、待审核、驳回、已发布、已确认、已下架、违规下架、交易完成
- **预约（2 种存续状态）**：待确认、已成功；失效即删除记录
- **账号（2 种）**：正常、已封禁

## 二、软件架构 UML 图

四张图分别对应实验要求的三类：结构类（类图、组件图）、行为类（状态图）、交互类（时序图）。

### 2.1 类图（结构类）

类图共 6 个类：用户、商品、预约、卖家认证申请、审核记录、操作日志；配套 9 个枚举（账号状态、当前权限、商品状态、预约状态、认证审核状态、审核结果、商品分类、成色、日志类型）。

![UML 类图](UML/UML类图.png)

关键设计决定与原因：

1. **不拆买家/卖家/管理员三个子类，只用「当前权限」一个字段区分。**
   访谈确认「卖家在买家基础上申请提权」，即卖家权限是买家权限的超集，二者不是并列关系；若拆子类，用户申请成为卖家时对象的类会在运行期改变，静态类图与运行期对象不一致。管理员与买家、卖家正交，不参与商品交易，也不属于权限层级中的任何一级。因此采用单类 + 枚举，权限差异用关联端点的角色名（发布者、买家、审核人、操作人）表达。

2. **预约只保留「待确认」「已成功」两种存续状态。**
   买家取消、卖家确认他人、商品违规下架、账号封禁等导致预约失效的场景，一律**直接删除预约记录**，不保留作废状态。这样「多条待确认预约并存」与「同一商品只有一条有效预约」不冲突——并存的是待确认记录，生效的只有一条。代价是买家查不到自己的历史预约，该功能不在本期需求内。

3. **审核记录与操作日志分成两个类。**
   操作日志是全平台的动作流水，操作对象通过「对象类型 + 对象ID」多态指向用户、商品、预约或认证申请；审核记录只服务商品审核，字段更少（结果、时间、理由），且驳回理由需要展示给卖家。两者内容有重叠，但可见性与生命周期不同，因此分开建模。

4. **卖家认证申请独立成类，不并入用户。**
   提权是一条有生命周期的记录（待审核 → 通过/驳回），需要保存姓名、审核人、审核时间与驳回理由。若退化为用户表上的几个字段，就无法回答「被驳回后重新申请过一次」这类问题。

5. **管理员联系方式与封禁提示文案不建模**，作为部署配置项处理：它们只有一两个常量、没有行为、不被业务数据引用。

### 2.2 组件图（结构类）

按职责分为两层、六个组件：表现层的 Web 界面，业务层的账号与权限、商品与审核、预约与交易、日志、统计五个模块。

![UML 组件图](UML/UML组件图.png)

模块之间通过**接口**协作，而非直接访问对方的内部实现：账号与权限模块提供「鉴权接口」，商品与审核模块提供「商品查询接口」，日志模块提供「日志查询接口」。

设计原因：

- **账号与权限独立成模块**：封禁必须对全平台所有操作生效，把鉴权做成唯一入口，可以避免各模块各自判断、漏判；
- **日志与统计分离**：预约记录失效即删除，历史预约量只能由日志提供，统计模块因此依赖日志的查询接口，而不是读预约表；
- **预约与交易模块对外只暴露四个动作**（发起、取消、确认、完成），预约失效删除是模块内部实现，界面层不感知。

### 2.3 状态图（行为类）

商品状态机主干：$\text{草稿} \to \text{待审核} \to \text{已发布} \to \text{已确认} \to \text{交易完成}$。

![UML 状态图](UML/UML状态图.png)

旁支：待审核 → 驳回 → 待审核（修改后重新提交）；已发布 → 已下架（卖家下架）；已发布 → 违规下架（管理员处置，终态）。禁止的转换：交易完成 → 已发布、违规下架 → 已发布、已下架 → 待审核。

预约状态机：待确认 →（卖家确认）→ 已成功；待确认 →（取消/未被选中/商品下架/账号封禁）→ 删除记录；已成功 →（违规下架/账号封禁）→ 删除记录；已成功 →（交易完成）→ 记录保留。图上只有一条主干，失效的两条迁移直接指向终止，不设「删除」状态，与类图口径一致。

商品状态在已发布、已确认两种状态下都可被违规下架（REQ-015 未限定入口），二者也都会因账号被封禁而下架（REQ-016），这两条迁移已在图中补全。

### 2.4 时序图（交互类）

选择并发预约场景，因为它同时覆盖预约相关的四条需求，是系统中最容易出错的路径。

![UML 时序图](UML/UML时序图.png)

1. 买家甲、乙先后预约同一商品，产生两条待确认记录；
2. 卖家确认甲的预约：甲记录变为已成功、通过「商品状态更新接口」把商品置为已确认、**乙的记录被删除**；
3. 乙用旧页面操作已删除的预约：系统查不到记录，按商品状态提示「商品已被约走」；
4. 线下成交后卖家点击完成交易，商品转为交易完成，甲的记录保持已成功不删除。

## 四、AI 参与工作流程的过程记录

三个环节都用到了 AI，AI 负责出初稿，具体判断与取舍由本人完成。

### 4.1 整理类的属性

- 使用场景：把实验一的需求文档交给 AI，让它产出类、属性、方法与关联关系的初稿。
- 生成结果：7 个类、9 个枚举、8 条关联关系的 PlantUML 代码。
- 修改优化：三个用户子类合并为「用户 + 当前权限」；删除申诉实体；预约状态由 5 个收敛为 2 个；昵称与联系方式改为必填；删掉只有常量没有行为的「系统配置」类；补 3 条类约束。
- 优缺点：出稿快、结构完整，缺点是按通用电商模板堆类，会把两个常量单建一个类，必须回到需求逐条裁剪。

### 4.2 美化 UI 界面

- 使用场景：让 AI 用统一的 HTML + CSS 生成各功能模块界面稿，并导出为图片。
- 生成结果：12 张风格一致的界面原型图，覆盖买家、卖家、管理员三类角色。
- 修改优化：注册页昵称与联系方式改必填；登录页补封禁提示；预约页只保留待确认、已成功两种状态；统计页补充统计口径说明。
- 优缺点：批量出图效率高、风格统一，缺点是生成的界面偏通用电商，不贴合本项目的权限与状态口径，需要逐屏校正文案与状态展示。

### 4.3 美化 PDF 报告

- 使用场景：让 AI 把 Markdown 报告排版成 PDF，并处理字体、公式与插图。
- 生成结果：10 页排版稿，含 4 张 UML 图与 12 张界面图。
- 修改优化：修正中文字体映射导致文本层乱码、等宽字体缺少中文字形、公式源码直接输出三处问题，最终改用浏览器打印输出。
- 优缺点：定位格式问题快，缺点是排版链路不稳定，同一套参数换一份内容会复发，每版都要重新验证。
